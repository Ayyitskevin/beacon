# Publish Project Policy before evaluating Team Lead candidates

Team Lead selection criteria are Project rules, not an appointment or a property of Team order.
An authenticated Operator may publish an immutable Project Policy revision only against the exact
current Charter revision and expected prior Policy revision. Each revision requires a distinct
closed Capability set containing `work.coordinate_mission`, current Team eligibility as the
availability rule, one or more distinct named Track Record evidence kinds with positive count
thresholds, no declared leadership conflict, and Operator adjudication when eligible candidates
remain ambiguous.

Policy publication does not inspect or invent Track Record evidence and does not evaluate or select
a candidate. A later selection path must use attributable evidence and current availability under
the latest Policy revision that applies to the current Charter.

## Consequences

Charter publication can make the latest Policy stale without rewriting it. Republishing preserves
the previous revision, binds the new revision to the new Charter, and records one attributable
`project.policy_published` Event. Only the latest Policy can report that it applies to the current
Charter.

Publication creates no Team Lead, Assignment, Route, Invocation, Run, credential, budget, network
scope, external effect, aggregate Team authority, or execution authority. Track Record evidence,
candidate evaluation, appointment, replacement, and authenticated Resident commands remain
separate decisions.

This proposal becomes accepted only with Product Steward sign-off on the reviewed branch.
