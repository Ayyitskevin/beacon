This draft adds the current UI/native boundary and evidence debt, not another W03 design.

The blueprint's constraint is narrower than “notify on an event”: only an Attention Item may **request** an OS notification. Activity, messages, completed work, background health and ordinary status stay inside Beacon unless they create an actionable Item; preferences can narrow interruption but cannot make a non-actionable event interrupt. An Item requires all three facts together—an unresolved condition, a named eligible actor, and a concrete next action. Enforced refusals and not-yet-run checks remain Activity rather than queue entries ([`docs/BLUEPRINT.md:347-360`](../../BLUEPRINT.md#L347)). The workflow promises that Briefing shows unresolved Attention Items, separately from Mission outcome, spend and Team activity ([`docs/BLUEPRINT.md:826-829`](../../BLUEPRINT.md#L826)); §9 repeats the OS boundary and rejects an Item without an eligible actor or next action ([`docs/BLUEPRINT.md:899`](../../BLUEPRINT.md#L899), [`:1162`](../../BLUEPRINT.md#L1162)). A failed Assignment's second failure is one specified route to Handoff or Attention, not a universal notification trigger ([`docs/BLUEPRINT.md:369-374`](../../BLUEPRINT.md#L369)). Pairing-expiry Attention is specified seven days before expiry, but this source reading does not establish a native pairing producer ([`docs/BLUEPRINT.md:66-72`](../../BLUEPRINT.md#L66)). Alpha sync may carry notification **preferences**, never notification contents, events or history ([`docs/BLUEPRINT.md:74-80`](../../BLUEPRINT.md#L74)); it is not a permission for remote delivery. The repository rules restate the same Attention-only boundary ([`AGENTS.md:80`](../../../AGENTS.md#L80)).

## Evidence owed before AC27 can be judged

**Positive path:** a native producer must demonstrably establish the three blueprint predicates for an actual unresolved condition, identify the eligible actor and concrete next action, retain the Item across the relevant restart/view boundary, expose that same unresolved Item in Briefing, and show whether a request to the OS boundary occurred under the applicable preference. The evidence must distinguish Item creation, visible in-app feedback, OS request and observed platform display; none follows automatically from the previous one. If a condition resolves, evidence must show the resulting queue/interrupt behavior without manufacturing an acknowledgment rule. The present sources do not supply that owner, Item read, request seam, or platform witness.

**Negative path:** show that routine Activity, completed/receipt-only events, background status (including the live-data warning), enforced refusals and not-yet-run checks do not issue OS requests; that an unresolved condition lacking an eligible actor or concrete next action is not misclassified; and that a preference can narrow but never widen interruptions. The AC40 inventory's cleared, foreign-owner and uncertain cases also need honest visibility/eligibility evidence before any notification claim. The blueprint's sync exclusion requires separate evidence that contents/events/history do not cross Cloud Link; no sync runtime was inspected. “No notification source found” proves none of these cases as a product behavior.

**Unresolved existing decisions, batched without asking Kevin:** no authoritative Item storage/lifecycle, producer-to-eligibility ownership, platform request/result feedback, preference read/enforcement point, or interaction of session lock/clearing/restart with outstanding requests was located in this bounded slice. M7's daily-operation flow and M8's conformance proof cannot be inferred from receipt UI. These remain design/evidence debts under the existing blueprint and authority/Tier rules, not an invitation to choose schema, permissions, notification text, dispatch, or new approval gates in this draft.
